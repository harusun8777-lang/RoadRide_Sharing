#　要件定義書

- 文書版: 0.2
- 作成日: 2026-09-20
- 更新日: 2026-09-25
- 対象: 地域AI乗り合い交通サービス MVP
- 対象範囲: 利用者向け予約・配車選択機能、運転手向け運行機能

## 1. 背景と目的

地域における交通手段の不足を補うため、同じ方向へ移動する利用者をまとめ、乗合タクシーを効率的に配車するWebアプリを提供する。

MVPでは、AIが予約条件から運転手付きの乗合候補（便）と運行ルートを提案し、乗車する利用者自身が候補を選んで配車を確定する。配車担当者は置かず、配車処理はアプリが担う。AIが利用者の選択なしに配車を確定することはしない。

## 2. 想定利用者

1つのアカウントで「利用者（rider）」と「運転手（driver）」の両方を登録できる。ただし同時に稼働できるのはどちらか一方だけとし、稼働中の区分は利用者が切り替える。

### 2.1 乗車利用者（rider）

地域住民。スマートフォンまたはPCから、乗車場所・目的地・希望時刻を入力して予約し、提示された配車候補から乗る便を選ぶ。

### 2.2 運転手（driver）

地域で乗合車両を運転する人。運転手として稼働中の間、配車候補の運転手となり、利用者に選ばれた便を運行する。運行開始と乗車完了を記録する。

## 3. MVPの範囲

### 対象に含めるもの

- 利用者・運転手の登録と、稼働区分の切り替え
- 利用者の乗車予約
- 予約内容の確認
- 予約のキャンセル
- 予約情報の一覧表示
- 同じ方向・近い時間帯の乗合候補（運転手付きの便）の作成
- 利用者による配車候補の選択・確定
- 乗合グループと乗車順の表示
- 運転手による担当運行の確認
- 運転手による運行開始・乗車完了の記録
- 利用者・運転手への状態通知

### 対象外とするもの

- 決済サービスとの本番連携
- GPSによる車両のリアルタイム追跡
- 電話予約の自動受付
- 顔認証・本人確認書類・運転免許の審査
- 高度な需要予測
- 自治体向けの統計・補助金帳票
- 利用者の選択なしにAIが配車を確定する完全自動運行
- 確定後の運転手都合による運行取り消し・再配車

## 4. 業務フロー

1. 利用者が乗車場所、目的地、希望時刻、人数を入力する。
2. システムが入力内容を検証し、予約を「マッチング中」で登録する。
3. AIマッチング処理が、運転手として稼働中のユーザーと既存予約をもとに、乗合候補（便）を作成する。
4. 利用者が候補ごとの運転手、出発時刻、料金目安、所要時間、相乗り人数を比較する。
5. 利用者が候補を1つ選び、配車を確定する。
6. システムが利用者と運転手へ確定内容を通知する。
7. 運転手が運行開始を記録し、運行後に乗車完了を記録する。

## 6. マッチング初期ルール

MVPでは、以下の固定ルールを基礎とする。実際の地図経路計算や機械学習は後続フェーズで導入する。

- 乗車希望時刻の差は原則15分以内
- 乗車場所の距離は運行地域の設定値以内
- 目的地が同じ、または同一方向の予約を優先
- 1グループの乗車人数は車両定員以下
- 乗合による追加所要時間は利用者ごとに最大15分以内
- 車いす対応などの必須条件がある場合は条件を満たす車両だけを候補にする
- 候補の運転手は、運転手として稼働中で、時間帯が重なる確定済みの運行がないユーザーに限る
- 候補が複数ある場合は、追加走行距離、待ち時間、利用者数の順に評価する

### 6.1 候補選定の理由

AIは候補を提示する際、単に条件を満たした便を並べるのではなく、利用者が選ぶための理由を明示する。候補の説明には、以下の観点を含める。

- 乗車場所と目的地が近く、同一方向または近い経路であること
- 希望時刻の差が小さく、待ち時間と追加所要時間が許容範囲内であること
- 車両定員や配慮事項を満たし、条件不一致がないこと
- 他の候補と比較して、待ち時間や料金目安の増加が少ないこと

これにより、利用者は候補の違いを短時間で理解し、納得して便を選べるようにする。

## 7. 状態定義

### 7.1 予約状態

| 状態 | 説明 |
| --- | --- |
| `matching` | 予約登録済み。配車候補の作成中、または利用者の選択待ち |
| `confirmed` | 利用者が候補を選び、配車が確定済み |
| `in_progress` | 運行中 |
| `completed` | 乗車・運行が完了 |
| `cancelled` | 利用者がキャンセル |

状態遷移は、原則として `matching → confirmed → in_progress → completed` とする。`matching` と `confirmed` から `cancelled` へ遷移できる。

### 7.2 便（乗合グループ）の状態

| 状態 | 説明 |
| --- | --- |
| `proposed` | AIが候補として作成済み。まだどの利用者にも選ばれていない |
| `confirmed` | 1人以上の利用者が選び、運行が確定済み |
| `in_progress` | 運転手が運行開始を記録済み |
| `completed` | 運転手が乗車完了を記録済み |
| `cancelled` | 取り消し済み |

運転手が稼働区分を切り替えた場合、その運転手の `proposed` の候補は取り消す。

## 8. データ要件

### 8.1 ユーザー

- 氏名、読み仮名、メールアドレス
- 登録済みの区分（利用者・運転手）
- 稼働中の区分

### 8.2 予約

- 予約番号
- 利用者識別子
- 乗車場所
- 目的地
- 希望乗車日時
- 乗車人数
- 配慮事項
- 予約状態
- 作成日時、更新日時
- キャンセル日時、キャンセル理由

### 8.3 乗合グループ（便）

- グループ番号
- 運転手識別子
- 含まれる予約番号
- 車両識別子
- 出発予定時刻
- 乗車順、降車順
- AIマッチング理由
- マッチングスコア

## 9. 非機能要件

### 9.1 ユーザビリティ

- 利用者の主要操作（予約から配車確定まで）を4画面以内で完了できること
- 高齢者でも読める文字サイズと十分なコントラストを確保すること
- 入力エラーを項目の近くに日本語で表示すること
- スマートフォンとPCの両方で利用できること
- 運転手画面は、停車中に短時間で確認・操作できること

### 9.2 性能

- 予約登録後、通常時5秒以内に配車候補を表示すること
- 運転手の担当運行一覧の初期表示を3秒以内に完了すること
- 同時予約数はMVPで1日500件を想定すること

### 9.3 可用性と安全性

- AIが利用できない場合でも、固定ルールによる単独配車の候補を提示できること
- 料金目安や乗車場所を確定前に利用者へ明示すること
- 予約・確定・キャンセル・運行記録の操作履歴を記録すること
- メールアドレスとパスワードでログインし、APIは JWT で本人を確認すること。パスワードはハッシュ化して保存すること
- 利用者情報は必要最小限だけ表示し、利用者には本人の予約だけ、運転手には担当する運行の利用者情報だけを表示すること
- 通信失敗時に二重予約・二重確定が発生しないこと
- 同じ便の最後の空席を複数の利用者が同時に選んでも、定員を超えて確定しないこと

## 11. 受入条件

- 1つのアカウントで利用者・運転手の両方を登録し、稼働区分を切り替えられる。
- 未完了の予約がある利用者は運転手へ、未完了の運行がある運転手は利用者へ切り替えられない。
- 利用者が乗車場所、目的地、日時、人数を入力して予約できる。
- 必須入力が不足している場合、予約が登録されずエラーが表示される。
- 予約登録後、運転手付きの配車候補が表示される。
- 候補に運転手、出発時刻、所要時間、料金目安、マッチング理由が表示される。
- 定員超過や条件不一致の候補が作成されない。
- 運転手として稼働していないユーザーは候補の運転手にならない。
- 利用者が候補を選ぶと、予約が「予約確定」になり、運転手の担当運行一覧に表示される。
- 運転手が運行開始・乗車完了を記録すると、利用者側の状態が「運行中」「乗車完了」に変わる。
- 利用者が予約をキャンセルすると、運転手側の運行にも反映される。
- PC幅とスマートフォン幅の画面で、主要操作が利用できる。
- AI処理に失敗しても、単独配車の候補から配車を確定できる。
