# ペルソナ定義書

## 1. 目的

Hitch Tacを利用する代表的な人物像を定義し、画面設計と機能優先順位を統一する。

本MVPでは、乗車する地域住民と、地域で乗合車両を運転する運転手を設定する。配車担当者は置かず、配車はアプリが提示した候補から利用者が選んで確定する。

1つのアカウントで利用者と運転手の両方を登録できるが、同時に稼働できるのはどちらか一方だけとする。

## 2. ペルソナA: 乗車利用者

### 基本情報

| 項目 | 内容 |
| --- | --- |
| 名前 | 佐藤 由美 |
| 年齢 | 68歳 |
| 居住地 | 地方都市の住宅地域 |
| 職業 | パート勤務、現在は週数日の勤務 |
| 家族構成 | 夫と2人暮らし |
| 利用端末 | Androidスマートフォン |
| デジタル経験 | LINEやWeb検索は使うが、複雑なアプリ操作は苦手 |
| 移動目的 | 病院、買い物、市役所への移動 |

### 生活背景

自宅から最寄りの公共交通機関まで距離があり、車を運転できない日は移動に困っている。電話予約はできるが、受付時間を気にせず自分の都合のよい時間に予約したい。

### 目的

- 自宅付近から目的地まで確実に移動したい
- 予約が成立したかをすぐ確認したい
- 乗車時刻、乗車場所、料金の目安を事前に知りたい
- いくつかの便から、自分に合うものを簡単に選びたい
- 予約を間違えた場合に自分でキャンセルしたい

### 困っていること

- 小さい文字や複雑な画面は読みづらい
- 住所を正確に入力できないことがある
- 「予約受付」と「予約確定」の違いが分かりにくい
- 配車が決まるまでの状況が分からないと不安になる
- 選択肢が多すぎたり違いが分かりにくいと、どれを選べばよいか迷う
- エラーが出たとき、何を直せばよいか分からない

### 行動シナリオ

1. スマートフォンでサービスを開く。
2. 乗車場所と目的地を入力する。
3. 希望日時と人数を選択する。
4. 入力内容を確認して予約する。
5. 予約番号と「マッチング中」の状態を確認する。
6. 表示された配車候補から、出発時刻と料金目安が合う便を選ぶ。
7. 配車確定後、乗車時刻と運転手を確認する。
8. 予定が変わった場合は予約詳細からキャンセルする。

### 必要な画面上の配慮

- 本文は16px以上にする
- 主要ボタンを大きくする
- 入力項目を一度に増やしすぎない
- 状態を「マッチング中」「予約確定」のような日本語で表示する
- 色だけでなく文字でも状態を伝える
- エラーを入力欄の近くに表示する
- 登録完了後に予約番号を大きく表示する
- 確定した乗車場所と時刻を目立たせる
- 配車候補は数を絞り、時刻・料金・待ち時間の違いを並べて見せる
- スマートフォンで横スクロールを発生させない

### 期待する価値

> 難しい操作をしなくても、予約できたか、いつどこから乗るかが分かる。

## 3. ペルソナB: 運転手

### 基本情報

| 項目 | 内容 |
| --- | --- |
| 名前 | 田中 健一 |
| 年齢 | 62歳 |
| 居住地 | 佐藤さんと同じ地方都市 |
| 職業 | 定年退職後、地域の乗合交通で運転手として働いている |
| 利用端末 | iPhone。車内ではホルダーに固定して使う |
| デジタル経験 | 地図アプリやメッセージアプリは使える |
| 担当業務 | 選ばれた便の運行、乗車・降車の確認、運行開始・乗車完了の記録 |

### 業務背景

空いている時間に運転手として稼働し、利用者に選ばれた便を運行している。通院などで自分が乗る側になる日もあり、その日は利用者として予約する。運転中はスマートフォンを操作できないため、停車中に短時間で次の行き先と乗客を確認したい。

### 目的

- 自分が担当する便と出発時刻をすぐに把握したい
- 乗車順、降車順、乗降場所を迷わず確認したい
- 車いすや大きな荷物などの配慮事項を事前に知りたい
- 運行開始・乗車完了を少ない操作で記録したい
- 運転する日と乗る日を、同じアカウントで切り替えたい

### 困っていること

- 小さな文字やボタンは車内で操作しづらい
- 担当する便が急に増えたり変わったりすると対応できない
- 乗客の配慮事項を現地で初めて知ると困る
- 運行が残っているのに誤って利用者に切り替えると、運行を見失う

### 行動シナリオ

1. アプリを開き、稼働区分を「運転手」に切り替える。
2. 担当する便が確定したら通知を受け取る。
3. 運転手ホームで次の便の出発時刻と乗車場所を確認する。
4. 運行詳細で乗客、人数、乗車順、配慮事項を確認する。
5. 出発時に「運行開始」を記録する。
6. 全員の降車後に「乗車完了」を記録する。
7. 担当する便がすべて終わってから、稼働区分を切り替える。

### 必要な画面上の配慮

- ボタンは大きく、1画面の主要操作を1つに絞る
- 次の便の出発時刻と乗車場所を最上部に表示する
- 配慮事項を目立たせる
- 運行開始・乗車完了は誤操作を防ぐため確認を挟む
- 未完了の運行があるときは、切り替えできない理由を表示する
- 通信エラー時に記録が二重にならないようにする

### 期待する価値

> 停車中に一目で次の行き先と乗客が分かり、少ない操作で運行を記録できる。

## 4. 共通する設計要件

両ペルソナに共通して、以下を満たす。

- 現在の状態が常に分かる
- 次に行う操作が明確である
- 操作完了後に結果を画面で確認できる
- 入力エラーや通信エラーの内容が具体的である
- 重要な操作を取り消しなく実行しない
- PCとスマートフォンの両方で主要操作ができる

## 5. ペルソナから導く優先順位

| 優先度 | 必要な機能 | 理由 |
| --- | --- | --- |
| 必須 | 大きく分かりやすい予約入力 | 佐藤さんが迷わず予約するため |
| 必須 | 予約状態と予約番号の表示 | 予約成立状況への不安を減らすため |
| 必須 | 比較しやすい配車候補の表示 | 佐藤さんが迷わず便を選ぶため |
| 必須 | マッチング理由の表示 | 候補の違いを理解して選ぶため |
| 必須 | 担当運行の一覧と詳細 | 田中さんが次の便を一目で把握するため |
| 必須 | 運行開始・乗車完了の記録 | 利用者側の状態を正しく更新するため |
| 必須 | 確定・キャンセルの通知 | 利用者と運転手の認識を一致させるため |
| 必須 | 稼働区分の切り替えと制限 | 運行や予約を残したまま切り替えないため |
| 任意 | 予約履歴 | 過去の利用を確認するため |
| 任意 | マッチングスコア | 複数候補を比較しやすくするため |

## 6. 受入確認

- [ ] 高齢者が予約画面の必須項目を理解できる
- [ ] 入力エラーの修正方法が分かる
- [ ] 予約番号と予約状態が確認できる
- [ ] 利用者が配車候補を比較して1つ選べる
- [ ] AI候補の理由を確認できる
- [ ] 運転手が担当する便と乗客を確認できる
- [ ] 運転手が運行開始・乗車完了を記録でき、利用者側に反映される
- [ ] 未完了の予約・運行がある間は稼働区分を切り替えられず、理由が表示される
