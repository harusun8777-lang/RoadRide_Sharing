# 3人・1週間 MVP開発計画

## 1. 開発目標

3人で1週間以内に、利用者の予約・配車候補の選択から、運転手による運行完了までを一通り体験できるMVPを作成する。

### 完成時の利用イメージ

1. 利用者が乗車場所、目的地、希望日時、人数を入力する。
2. 予約が登録され、予約番号と「マッチング中」が表示される。
3. 運転手として稼働中のユーザーと条件の近い予約から、配車候補が表示される。
4. 利用者が候補を選んで配車を確定する。
5. 利用者側に「予約確定」と乗車情報、運転手側に担当運行が表示される。
6. 運転手が運行開始・乗車完了を記録し、利用者側の状態が変わる。

## 2. 担当分担

### 担当A: 利用者向け画面

- 乗車予約画面
- 予約確認画面
- 予約完了画面
- 配車候補選択画面
- 予約詳細・キャンセル画面
- 入力エラー表示
- スマートフォン向けレイアウト

### 担当B: 運転手向け画面・共通画面

- アカウント・稼働区分切り替え画面
- 運転手ホーム・担当運行一覧
- 運行詳細・状態更新画面（運行開始・乗車完了）
- 運行履歴画面
- 車内で操作しやすいスマートフォン向けレイアウト

### 担当C: バックエンド・マッチング

- データモデルとデータベース
- ユーザー登録・稼働区分切り替えAPI
- 予約登録・取得・キャンセルAPI
- 配車候補取得・選択（確定）API
- 運行開始・乗車完了API
- 簡易マッチング処理
- 定員超過チェック
- マッチング理由の生成
- 結合用のテストデータ作成

## 3. 1週間の予定

| 日 | 作業内容 | 完了条件 |
| --- | --- | --- |
| 1日目 | 技術構成、画面、API、データ構造を確定 | 全員がAPI仕様と担当範囲を確認済み |
| 2日目 | 各担当が画面・API・DBの実装を開始 | 各担当の主要画面または機能が表示・動作する |
| 3日目 | 予約登録、稼働区分切り替え、状態管理を実装 | 予約を登録し、区分を切り替えられる |
| 4日目 | 簡易マッチングと候補表示を実装 | 稼働中の運転手付きの候補が表示される |
| 5日目 | 候補の選択・確定、運行記録、キャンセルを実装 | 利用者の確定が運転手側に、運転手の記録が利用者側に反映される |
| 6日目 | 画面接続、入力チェック、スマホ対応 | 予約から運行完了まで一連の操作ができる |
| 7日目 | 結合テスト、修正、デモ準備、GitHub公開 | 受入条件を確認し、デモを実行できる |

## 4. MVPに含める機能

- 利用者の予約登録
- 予約番号の発行
- 予約内容の確認
- 予約状態の表示
- 予約キャンセル
- 利用者・運転手の登録と稼働区分の切り替え
- 未完了の予約・運行がある間の切り替え禁止
- 時刻差による候補抽出
- 乗車場所・目的地が近い予約の候補抽出
- 車両定員を超えないグループ作成
- 稼働中の運転手だけを候補にする
- マッチング理由の表示
- 利用者による候補の選択・確定
- 運転手の担当運行一覧
- 運転手による運行開始・乗車完了の記録
- `matching`、`confirmed`、`in_progress`、`completed`、`cancelled` の状態管理
- PC・スマートフォンでの基本操作

## 5. 今回は対象外にする機能

- 本格的な機械学習によるAI配車
- 地図サービスによる正確な経路計算
- GPSによる車両追跡
- 決済サービス連携
- SMS・メール通知
- 運転手都合による運行取り消しと再配車
- 本番運用向けの高度な認証・権限管理
- 自治体向け統計・帳票

## 6. 簡易マッチングルール

- 希望乗車時刻の差が15分以内
- 乗車場所が設定した距離以内
- 目的地が同じ、または同一方向
- 合計人数が車両定員以下
- 車いすなどの配慮事項が一致
- 候補にはマッチング理由を表示
- 条件に合う候補がない場合は単独配車の候補を表示

## 7. 受入確認

- [ ] 必須項目が不足した予約を登録できない
- [ ] 正しい予約が予約番号付きで登録される
- [ ] 利用者・運転手を登録し、稼働区分を切り替えられる
- [ ] 未完了の予約・運行がある間は切り替えられない
- [ ] 予約登録後、稼働中の運転手付きの候補が表示される
- [ ] 条件の近い2件以上の予約から相乗りの候補が作成される
- [ ] 定員超過の候補が作成されない
- [ ] 利用者が候補を選んで確定できる
- [ ] 確定した便が運転手の担当運行一覧に表示される
- [ ] 運転手の運行開始・乗車完了が利用者側に反映される
- [ ] 利用者のキャンセルが運転手側にも反映される
- [ ] AI処理に失敗しても単独配車の候補から確定できる
- [ ] PC幅とスマートフォン幅で主要操作ができる

## 8. 開発上の注意

- 1日目にAPIの入出力形式を決め、途中で大きく変更しない。
- 毎日、各担当の変更を共有ブランチへ統合する。
- 画面だけ、またはAPIだけを作り込まず、早い段階で予約登録から状態変更まで接続する。
- AIという名称でも、MVPでは固定ルールによる候補抽出でよい。
- 7日目まで新機能を追加せず、結合テストと不具合修正を優先する。
